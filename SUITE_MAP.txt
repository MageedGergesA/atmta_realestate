1. SUITE OVERVIEW
════════════════════════════════════════════════════════════════════════════════

The suite is composed of 14 loosely-coupled modules that share:
- One property model (realestate.property) — hierarchy compound→building→floor→unit→room
- One project model (realestate.project) — plus phases
- One partner engine (res.partner via Odoo core)
- One accounting engine (account.move / account.payment via Odoo core)
- One purchase engine (purchase.order via Odoo core)
- One stock engine (stock.picking / stock.move via Odoo core)

Modules can be installed independently (min set is atmta_real_estate).
Each downstream module extends the shared master data instead of duplicating it.

Module list:
   1. atmta_real_estate              — RENTAL CORE + property master
   2. real_estate_developer          — SALES: project→phase→reservation→sale
   3. real_estate_brokerage          — SALES AGENCY: listings/leads/offers
   4. real_estate_construction       — CONSTRUCTION: milestones/BOQ/certs
   5. real_estate_procurement        — SUPPLY CHAIN: material requests + POs
   6. real_estate_handover           — HANDOVER: snagging + warranty
   7. real_estate_portal             — CUSTOMER SELF-SERVICE
   8. real_estate_api                — PUBLIC REST API + embed tokens
   9. real_estate_investment         — FEASIBILITY: NPV / IRR / DCF
  10. real_estate_maquette           — 3D VIEWER (glTF)
  11. real_estate_plan               — 2D DRILL-DOWN (image + polygons)
  12. real_estate_contract_template  — WORD/PDF DOC GEN (Jinja2)
  13. real_estate_checks             — PDC MANAGEMENT ⭐
  14. real_estate_customer_service   — POST-HANDOVER TICKETS ⭐

3. MASTER DATA / HIERARCHY
════════════════════════════════════════════════════════════════════════════════

  realestate.project (real_estate_developer)
      │  code, name, project_type (residential/commercial/mixed/land/industrial)
      │  expected_budget, currency, stock_location_id
      │  analytic_account_id (auto-generated by construction)
      │
      ├─ realestate.phase (real_estate_developer)
      │
      └─ realestate.property (atmta_real_estate)
              │  hierarchy_level: compound → building → floor → unit → room
              │  inherits product.template (so it plays with sales/stock)
              │  40+ fields (rooms, utilities, ownership, location, media)
              │  state: available / reserved / rented / maintenance / inactive
              │
              └─ children via parent_id (tree structure)


All money-tracking downstream models FK to realestate.project (for cost centers)
or realestate.property (for per-unit tracking). Nothing lives orphaned.

────────────────────────────────────────
4.1  atmta_real_estate  (RENTAL CORE)
────────────────────────────────────────

  MODELS:
    realestate.property           — the shared property master
    realestate.contract           — rental contract
    realestate.contract.payment   — scheduled payment on rental contract
    realestate.contract.payment.line — charge line under a payment

  RENTAL CYCLE:
    (1) Create property (unit)
          state: available
    (2) Create rental contract (partner, start, end, deposit_state)
          state: draft
    (3) Generate payment schedule
          action_generate_payment_lines() → creates realestate.contract.payment rows
          each row has its due date and payment deadline
    (4) Confirm contract
          state: draft → ready → confirmed → invoiced → active
          Property state: available → rented
    (5) Each period the linked payment auto-invoices
          contract_payment.state: draft → invoiced → paid
          Related invoice via move_id + move_state + payment_state
    (6) Charges added (maintenance, utility, etc.)
          via charge_line_ids on contract_payment
          amount_total = base + Σ(charges)
    (7) Contract expires
          state: active → expired
          Property state: rented → available
    (8) Deposit refunded or forfeited
          deposit_state: held → refunded / forfeited / partial_refund

4.2  real_estate_developer  (SALES)
────────────────────────────────────────

  MODELS:
    realestate.project             — top-level project
    realestate.phase               — project phase
    realestate.unit.reservation    — hold-and-book (first-class object)
    realestate.sale.contract       — sale contract
    realestate.sale.installment    — installment on sale contract

  SALES CYCLE:
    (1) Create project (residential/commercial/mixed/land/industrial)
    (2) Create phases + units under project
    (3) Create reservation
          state: hold
          hold_expiry_at = now + hold_duration_hours (default 72h)
          booking_fee captured
          proposed_price vs base_price → proposed_vs_base %
          Property state: available → reserved
    (4) Reservation confirmed (buyer commits)
          state: hold → booked → confirmed
    (5) Sale contract created from reservation
          reservation.sale_contract_id set
          sale_contract.state: draft
          Property state: reserved → sold (via sale_status field)
    (6) Installments generated on sale contract
          installments: down / installment / balloon kinds
    (7) Each installment invoiced individually
          action_generate_invoice() → posts account.move
          installment.state: pending → invoiced → paid
    (8) Payment received → automatic reconciliation
    (9) Contract completed
          sale_contract.state: signed → completed

4.4  real_estate_construction  (CONSTRUCTION)
────────────────────────────────────────

  MODELS:
    realestate.contractor
    realestate.construction.milestone
    realestate.construction.task
    realestate.construction.cost.line
    realestate.construction.payment.certificate
    realestate.construction.payment.certificate.line  ⭐
    realestate.boq                                     ⭐
    realestate.boq.line                                ⭐
    realestate.work.item + .category                   ⭐
    realestate.owner.progress.billing                  ⭐
    realestate.owner.progress.billing.deduction        ⭐
    realestate.construction.labor.log                  ⭐
    realestate.construction.dashboard (AbstractModel)
    (extends realestate.project with analytic_account_id) ⭐

  CONSTRUCTION CYCLE:
    (1) Contractor onboarded
          specialization (civil/MEP/finishing/...), rating (A/B/C)
          default retention_pct (e.g. 5%)
    (2) Milestones defined on project
          category (excavation/foundation/structure/MEP/finishing/...)
          weight (%), expected dates, budget_amount, contractor_id
          milestone.state: not_started
    (3) BOQ created for milestone (engineering budget)
          boq.state: draft
          lines with work_item + quantity + unit_rate
          total_amount = Σ(qty × rate)
    (4) BOQ approved
          boq.state: draft → approved → locked
          Lines now available for certification
    (5) BOQ → material request auto-generated
          For lines with linked products, spawns a MR
    (6) Milestone tasks tracked
          task.state: pending → in_progress → done / skipped
          task.completion_pct rolls up to milestone.completion_percentage
    (7) Labor logged daily
          workers × hours × hourly_rate → total_cost
          Auto-creates cost_line (category='labor')
          Cost_line inherits project analytic_account
    (8) Cost lines accumulate (material/labor/equipment/subcontract/permit/other)
          project.actual_cost = Σ(cost_lines)
          project.cost_variance = actual - expected_budget
    (9) Payment certificate created (contractor progress billing)
          pc.state: draft
          contract_value + previously_certified_pct + current_certified_pct
          OR line_ids populated with BOQ lines (quantity mode)
          gross_amount = contract_value × current_pct
                       OR Σ(line.qty × line.unit_rate) if BOQ mode
          retention_amount = gross × retention_pct
          net_payable = gross - retention
    (10) Payment certificate certified
           pc.state: draft → certified
           If PO-linked: qty_received bumped on the PO line
    (11) Vendor bill created from certificate
           pc.state: certified → invoiced
           account.move in_invoice created with:
             - main line (or per-BOQ-line breakout)
             - retention withheld line (negative amount)
           analytic_distribution applied to every line
    (12) Vendor paid
           pc.state: invoiced → paid
    (13) OWNER-side progress billing (parallel)
           opb.state: draft
           contract_value × current_pct → gross
           Deductions (mobilization/materials/retention/penalty/other)
           net_invoiced = gross - Σ(deductions)
    (14) Owner billing certified + invoiced to customer
           opb.state: draft → certified → invoiced → paid
           account.move out_invoice with main line + deduction lines
    (15) Milestone completed
           milestone.state: in_progress → completed
           Project construction_progress recomputes (weighted avg)

4.5  real_estate_procurement  (SUPPLY CHAIN)
────────────────────────────────────────

  MODELS:
    realestate.material.request
    realestate.material.request.line
    realestate.procurement.approval.rule   ⭐
    realestate.procurement.approval.step   ⭐
    (extends purchase.order with re_project_id, re_source_model, re_source_id)
    (extends purchase.order.line with re_material_request_line_id)
    (extends res.partner with is_realestate_vendor + 7 tag taxonomy)
    (extends product.template with 4 flag taxonomy)

  PROCUREMENT CYCLE:
    (1) Approval rules defined (one-time setup)
          rule: min_amount, max_amount, group_id, sequence
          Multiple rules can match one MR
    (2) Material request raised (from any source)
          source_ref: polymorphic to construction task/milestone,
                      handover defect, rental contract, ticket, etc.
          project + property auto-derived from source
          analytic_account auto-derived from project
          mr.state: draft
    (3) Lines added (product, qty, uom, description)
          estimated_total = Σ(line qty × price_hint)
    (4) MR submitted
          mr.state: draft → submitted
          If priority='urgent': skips approval, jumps to 'approved'
          Otherwise: approval steps generated from matching rules
    (5) Approval steps approved individually
          Each step's approver_id/approval_date recorded
          When all_approvals_done: auto-promote to 'approved'
          mr.state: submitted → approved
    (6) Purchase orders created (grouped by supplier)
          action_create_purchase_orders()
          Lines grouped by product.preferred_supplier
          One PO per supplier
          analytic_distribution applied to each PO line
          Confirmed automatically
          mr.state: approved → ordered
    (7) Stock picking generated (project-routed)
          _prepare_stock_moves override sets location_dest_id
            to project.stock_location_id
    (8) Receipts validated → qty_received propagates back
          mr.state: ordered → partial → received
    (9) Vendor bill posted → payment
          mr.state: received → done

4.9  real_estate_investment  (FEASIBILITY)
────────────────────────────────────────

  MODELS:
    realestate.investment.feasibility
    realestate.investment.scenario
    realestate.investment.cash.flow
    realestate.investment.dashboard

  INVESTMENT CYCLE:
    (1) Feasibility study created
          name + discount_rate (default 10%) + analysis_period_years + base_year
          state: draft
    (2) Cash flows added per period (year 0 to year N)
          period_index + year + inflow + outflow
          net_flow = inflow - outflow
          discounted_flow = net_flow / (1 + discount_rate) ^ period
    (3) Metrics auto-computed
          NPV = Σ(discounted_flow)
          IRR = Newton-Raphson root of NPV(rate)=0, then × 100
          payback_period = periods until Σ(net_flow) ≥ 0 (fractional)
          total_inflow, total_outflow, net_undiscounted
          Positive_NPV flag drives green/red ribbon
    (4) Scenarios created (optional)
          types: best / expected / worst / custom
          Each scenario has its own metrics
    (5) Study approved
          state: draft → approved / rejected → archived

4.13  real_estate_checks  ⭐ (PDC)
────────────────────────────────────────

  MODELS:
    realestate.check
    realestate.check.deposit
    realestate.check.bounce
    realestate.check.bulk.wizard
    realestate.check.deposit.wizard
    realestate.check.bounce.wizard
    (extends realestate.sale.contract with check smart stats)

  PDC CYCLE:
    (1) Bulk-create checks from sale contract installments
          Wizard: sale_contract + bank + first_check_number + journal
          Generates N checks with sequential numbers
          check.state: registered
          Each check linked to its sale_installment_id
    (2) Register additional individual checks manually (optional)
          check.state: draft → registered
    (3) Group registered checks into deposit slip
          Deposit wizard: pick checks + journal + bank_slip_ref
          deposit.state: draft
    (4) Confirm deposit
          deposit.state: draft → confirmed
          All contained checks: registered → deposited
    (5a) Clear-all successful path
          deposit.action_clear_all()
          Each check.action_mark_cleared():
            - creates account.payment inbound
            - reconciles with linked installment invoice
          check.state: deposited → cleared
          deposit.state: confirmed → cleared
    (5b) Bounce path (partial or full)
          Register bounce via bounce_wizard
          bounce reason: insufficient/stop_payment/signature/closed/technical/other
          check.state: deposited → bounced
          deposit.state: confirmed → partial (if only some bounced)
          Optional: penalty_amount → auto-invoice drawer
    (6) Replacement check (bounced only)
          Create new check → link via replaces_check_id
          Old check's replacement_check_id set
          Old check.state: bounced → replaced
    (7) Reconciliation
          Cleared checks' payments reconcile with installment invoices
          Sale contract check_amount_cleared updates

    (2) Ticket created (title, reporter, property, category, priority)
          ticket.state: new
          SLA deadline auto = create_date + category.default_sla_hours
          Default assignee applied → if set, auto-flip to 'assigned'
    (3) Assigned to agent
          ticket.state: new → assigned
    (4) Agent starts work
          ticket.state: assigned → in_progress
    (5) Waiting for customer feedback (optional)
          ticket.state: in_progress → waiting
    (6) Ticket resolved
          ticket.state: any → resolved
          resolved_on set
    (7) Ticket closed
          ticket.state: resolved → closed
          closed_on set
    (8) Reopen if issue returns
          ticket.state: resolved/closed → assigned (or new via reopen)
          resolved_on/closed_on cleared
    (9) SLA breach detection
          If unresolved past sla_deadline: sla_breached=True
          Kanban color-codes breached tickets
    (10) Ticket → Material request escalation
           action_create_material_request()
           Spawns MR w/ source_ref pointing back to ticket
           MR project/property auto-derived from ticket's property

6. FINANCIAL FLOW MAP
════════════════════════════════════════════════════════════════════════════════

MONEY-IN (Customer → Developer)
───────────────────────────────

  Path A — Sale installment via invoice
    sale_installment.action_generate_invoice
      → account.move (out_invoice, posted)
      → account.payment (inbound, reconciled)
      → installment.state: pending → invoiced → paid

  Path B — Sale installment via PDC check ⭐
    sale_contract.action_bulk_create_checks (wizard)
      → N × realestate.check (state=registered, sale_installment_id set)
    Later:
      → deposit_wizard → deposit.action_confirm
        → checks flip to state=deposited
      → deposit.action_clear_all
        → each check.action_mark_cleared:
          → account.payment (inbound)
          → attempt reconcile with sale_installment.move_id
          → check.state=cleared
        → deposit.state=cleared

  Path C — Bounced PDC ⭐
    check.action_open_bounce_wizard → bounce_wizard
      → realestate.check.bounce created (reason + penalty_amount)
      → check.state=bounced
      → deposit.state=partial (if only some bounced)
      → Optional: bounce.action_issue_penalty_invoice
        → account.move (out_invoice, drawer partner_id)

  Path D — Owner progress billing (build-to-order) ⭐
    opb.action_certify → opb.action_create_customer_invoice
      → account.move (out_invoice)
      → 1 line for gross + 1 line per deduction (negative amounts)
      → analytic_distribution on every line

  Path E — Brokerage commission (agent-to-developer, or reverse if agent-received)
    transaction closed → commission auto-computed
      → payment via account.payment

  Path F — Rental payment
    contract_payment.action_register_payment → account.payment
      → reconciled against contract_payment invoice

MONEY-OUT (Developer → Contractor / Supplier)
─────────────────────────────────────────────

  Path A — Material request → PO → vendor bill
    material_request.action_create_purchase_orders
      → grouped by preferred_supplier → 1 PO per supplier
      → PO confirm → picking (routed to project's stock location)
      → receipt validated → vendor bill via Odoo core

  Path B — Payment certificate → vendor bill
    payment_certificate.action_certify
      → pc.state=certified
      → If PO-linked: qty_received bumped
    payment_certificate.action_create_vendor_bill
      → account.move (in_invoice)
      → line 1: gross amount OR per-BOQ-line breakout
      → line 2..N: retention withheld (negative)
      → analytic_distribution applied
    payment_certificate.action_mark_paid
      → account.payment posted

  Path C — Labor cost (implicit)
    labor_log.create → auto-syncs cost_line (category='labor')
      → cost_line rolls up to project.actual_cost
      → No cash outlay yet (books later via payroll)

  Path D — Subcontract PO
    subcontract_po_wizard → 1 master PO per contractor
      → 1 line per milestone in scope
      → analytic_distribution per line

  Path E — Bounce penalty received (money-in flow, but adjacent)
    See Path C above

7. ANALYTIC-ACCOUNT PROPAGATION (COST CENTER MAP)
════════════════════════════════════════════════════════════════════════════════

Each project gets a single analytic account (auto-generated).
That analytic account propagates DOWNSTREAM through 5 layers:

    realestate.project.analytic_account_id
        │
        │ (auto-generated on demand via
        │  action_generate_analytic_account, using sudo())
        │
        ├──▶ realestate.construction.cost_line.analytic_account_id
        │       (compute from cost_line.project_id.analytic_account_id)
        │
        ├──▶ realestate.material.request.analytic_account_id
        │       (compute from mr.project_id.analytic_account_id)
        │        │
        │        └──▶ purchase.order.line.analytic_distribution
        │                (set at PO creation time in action_create_purchase_orders)
        │                 │
        │                 └──▶ account.move.line.analytic_distribution
        │                         (via Odoo core 3-way match: PO→bill)
        │
        ├──▶ realestate.construction.payment.certificate.analytic_account_id
        │       (compute from pc.project_id.analytic_account_id)
        │        │
        │        └──▶ account.move.line.analytic_distribution
        │                (set on every bill line in action_create_vendor_bill,
        │                 including retention withheld line and per-BOQ lines)
        │
        └──▶ realestate.owner.progress.billing.analytic_account_id
                 │
                 └──▶ account.move.line.analytic_distribution
                         (customer invoice lines get tagged, including
                          deduction lines)

Result: One analytic account per project → full project P&L in one report.

14. WHAT'S SHARED ACROSS MODULES ("THE SPINE")
════════════════════════════════════════════════════════════════════════════════

The following 5 things are shared across the entire suite. Change any of them
and MANY modules react:

  (1) realestate.property (atmta_real_estate)
      — Extended by developer, construction, procurement, handover, checks,
        customer_service, plan, maquette, api.
      — Hierarchy + state + all extension fields live on ONE model.

  (2) realestate.project (developer)
      — Extended by construction (analytic_account_id, milestone rollups)
      — Referenced by procurement, checks, handover, api.
      — Master data for cost centers.

  (3) res.partner (Odoo core)
      — Extended by procurement (vendor tags), api (RE fields).
      — Every partner-facing document links here (contract, ticket, check, etc.).

  (4) The analytic account per project (construction extension)
      — Propagates through cost_line, MR, PO line, vendor bill, customer invoice.
      — This is the "project P&L" backbone.

  (5) The polymorphic source_ref on material_request (procurement)
      — Handover defects, rental contracts, customer tickets, construction tasks,
        construction milestones all register as valid source models.
      — Downstream modules only need to ADD to the selection; no schema change.
